# Store Now, Decrypt Later Security Notes

CentralSSH now partially mitigates Store Now, Decrypt Later (SNDL) risk on both SSH transport legs. Its centralized SSH transport policy prefers the OpenSSH-aligned hybrid key exchange `mlkem768x25519-sha256`, retains AEAD ciphers, disables SSH compression, keeps SHA-2 ETM MAC fallback, and rekeys after 30 minutes or 512 MiB.

Do not describe this project as fully post-quantum secure. The current design only upgrades transport confidentiality where both peers negotiate the hybrid KEX. SSH host and user signatures remain classical, `sntrup761x25519-sha512` is not currently exposed by the pinned Rust SSH stack, and deployments that retain classical fallback can still negotiate classical sessions with older clients or targets.

## Operational Requirements

- Treat `/etc/centralssh/config.toml`, `/etc/centralssh/known_hosts`, `/etc/centralssh/host_ed25519`, `/var/lib/centralssh/keys`, `/var/log/centralssh/audit.jsonl`, and `/var/lib/centralssh/fail2ban_state.json` as sensitive backup inputs.
- Encrypt backups with authenticated symmetric encryption such as AES-256-GCM or ChaCha20-Poly1305. Keep backup keys separate from backup ciphertext.
- Do not encrypt long-lived backups only to RSA, ECDH, age, PGP, or CMS public-key recipients unless there is a hybrid/PQC wrapping layer or separate symmetric key custody that can survive quantum migration.
- Define retention. Keep audit logs and fail2ban state only as long as operationally necessary. Keep old encrypted backups only as long as their secrecy lifetime justifies.
- Rotate gateway host keys and per-user target keys on a documented schedule and after suspected compromise. Existing code does not auto-rotate or rewrap old key material.
- Do not commit private keys, real host inventories, live IP addresses, tokens, `.env` files, production configs, or backup passphrases.

## PQC / Hybrid Blockers

- `russh 0.60.2` exposes `mlkem768x25519-sha256`, but not `sntrup761x25519-sha512`. CentralSSH therefore cannot yet offer the second OpenSSH-preferred hybrid KEX name the prompt asked for.
- The current `russh` server handler API does not expose a frontend per-session `kex_done` callback. CentralSSH can audit the loaded frontend KEX policy and the negotiated backend KEX, but not the exact frontend negotiated KEX per session without upstream changes or a maintained fork.
- Host and user SSH keys remain classical identity mechanisms. They do not provide session confidentiality, and Ed25519/RSA/ECDSA signatures are not PQ-safe.
- TOTP SHA-1 remains for authenticator compatibility. It is not used as a collision-resistant signature or encryption primitive.

## Migration Plan

Immediate:

- Keep `src/crypto_policy.rs` as the only place for SSH algorithm policy.
- Prefer `mlkem768x25519-sha256` first on both frontend and backend SSH transport.
- Reject unsupported configured frontend KEX names, including `sntrup761x25519-sha512`, during config validation instead of silently ignoring them.
- Reject MD5 fingerprints and SHA-1 SSH-RSA host-key algorithms for new negotiations.
- Encrypt and expire backups that contain config, private keys, logs, or fail2ban state.

Short-term:

- Add operator tooling for key rotation and inventorying stale keys.
- Add stronger OpenSSH-based integration tests that assert the negotiated frontend algorithm and strict-PQ failure paths.
- Add log rotation examples with encrypted archival.

Medium-term:

- Track upstream `russh` support for `sntrup761x25519-sha512` and frontend server-side negotiated-KEX callbacks.
- Add config fields for explicit crypto-policy versions so deployments can opt into future policies without code changes.
- Add migration checks that warn when target hosts only support deprecated algorithms.

Long-term:

- Expand to additional interoperable hybrid SSH KEX names when the Rust SSH stack exposes them.
- Adopt PQ-safe host/user authentication when the SSH ecosystem has stable support.
- Move long-lived secret custody toward KMS/HSM/Vault-style storage with auditable key versions and rotation.

## Audit Visibility

CentralSSH now emits transport-related audit data in these places:

- `frontend_kex_policy_loaded`: records the frontend listener's offered KEX list, whether classical fallback remains enabled, and whether frontend strict PQ is set
- `backend_kex_policy_applied`: records the outbound gateway-to-target offered KEX list, whether classical fallback remains enabled, and whether backend strict PQ is set
- `backend_kex_negotiated`: records the gateway-to-target negotiated KEX name and whether it is post-quantum hybrid or classical fallback

Current limitation:

- frontend per-session negotiated KEX is not yet observable through the current `russh` server API, so CentralSSH cannot honestly emit that event yet
