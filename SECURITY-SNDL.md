# Store Now, Decrypt Later Security Notes

CentralSSH is partially defended against Store Now, Decrypt Later (SNDL) attacks. It now enforces a narrow SSH transport policy with ephemeral Curve25519 key exchange, AEAD ciphers, no SSH compression, SHA-2 ETM MAC fallback, and 30-minute or 512 MiB rekeying. It is not quantum-safe because the current SSH stack is classical-only and does not implement hybrid or post-quantum key exchange.

Do not describe this project as post-quantum secure.

| Area | Current State | SNDL Risk | Mitigation | Remaining Work |
| ---- | ------------- | --------: | ---------- | -------------- |

## Operational Requirements

- Treat `/etc/centralssh/config.toml`, `/etc/centralssh/known_hosts`, `/etc/centralssh/host_ed25519`, `/var/lib/centralssh/keys`, `/var/log/centralssh/audit.jsonl`, and `/var/lib/centralssh/fail2ban_state.json` as sensitive backup inputs.
- Encrypt backups with authenticated symmetric encryption such as AES-256-GCM or ChaCha20-Poly1305. Keep backup keys separate from backup ciphertext.
- Do not encrypt long-lived backups only to RSA, ECDH, age, PGP, or CMS public-key recipients unless there is a hybrid/PQC wrapping layer or separate symmetric key custody that can survive quantum migration.
- Define retention. Keep audit logs and fail2ban state only as long as operationally necessary. Keep old encrypted backups only as long as their secrecy lifetime justifies.
- Rotate gateway host keys and per-user target keys on a documented schedule and after suspected compromise. Existing code does not auto-rotate or rewrap old key material.
- Do not commit private keys, real host inventories, live IP addresses, tokens, `.env` files, production configs, or backup passphrases.

## PQC / Hybrid Blockers

- `russh 0.53.0` does not implement ML-KEM/Kyber or any standardized hybrid SSH key exchange. CentralSSH therefore cannot protect captured SSH sessions from a future quantum attacker that can solve the recorded classical Curve25519 exchange.
- OpenSSH has experimented with hybrid post-quantum KEX names, but this Rust stack does not expose compatible algorithms today.
- Host/user SSH keys are classical identity mechanisms. They do not provide session confidentiality, and Ed25519/RSA/ECDSA signatures are not PQ-safe.
- TOTP SHA-1 remains for authenticator compatibility. It is not used as a collision-resistant signature or encryption primitive.

## Migration Plan

Immediate:

- Keep `src/crypto_policy.rs` as the only place for SSH algorithm policy.
- Reject MD5 fingerprints and SHA-1 SSH-RSA host-key algorithms for new negotiations.
- Encrypt and expire backups that contain config, private keys, logs, or fail2ban state.

Short-term:

- Add operator tooling for key rotation and inventorying stale keys.
- Add integration tests that assert negotiated SSH algorithms when a test target is available.
- Add log rotation examples with encrypted archival.

Medium-term:

- Evaluate Rust SSH libraries or `russh` upgrades that support standardized hybrid SSH KEX.
- Add config fields for explicit crypto-policy versions so deployments can opt into future policies without code changes.
- Add migration checks that warn when target hosts only support deprecated algorithms.

Long-term:

- Adopt hybrid SSH KEX when it is mature and interoperable.
- Adopt PQ-safe host/user authentication when the SSH ecosystem has stable support.
- Move long-lived secret custody toward KMS/HSM/Vault-style storage with auditable key versions and rotation.
